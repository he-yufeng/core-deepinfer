# 06 从一个能跑的核心，继续改自己的推理实验

[English](06-fork-and-extend_EN.md) · [系列目录](00-index.md)

对标 CoreCoder，不是把 README 写成相似的排版，也不是追同样的行数。更有用的标准是：你改一个决定，能不能沿着完整执行链看到后果，并由独立对照指出哪里错了。

先运行 [`examples/engine_batch.py`](../examples/engine_batch.py)。它通过库接口提交请求、取消一个请求、手动推进一轮、排空余下请求，再复用同一个引擎。每个健康结果都与普通 greedy 对照，不需要读 CLI 的实现才能嵌入自己的程序。

## 最便宜的修改：调度策略

保持模型不变，把 `EngineConfig.max_batch_tokens` 从八调到二，再观察同一批不同长度的请求。调度轮数和验证宽度会变，但默认 exact 模式下，正确的最终 Token 与状态不应因此改变。

再换一份 `cost_curve`，例如把更大尺寸设得非常昂贵。你应该看到更少的有效草稿被验证，而不是看到 padding 变成额外输出。没有真实硬件测量时，曲线只能当实验输入，不能写成“自动找到了最快配置”。

## 第二个修改：恢复策略

当前 `_open` 选最长已存前缀。你可以比较较短 hot 状态与较长 warm 前缀的恢复工作，再写一条选择策略。需要新增的是代价模型和对照，不是把 `hit=True` 改成一个更复杂的名字。

如果改用 compact 恢复，预期可以改变模型轨迹。不要让 exact 的回归测试偷偷放宽容差来容纳这种语义变化。保留两类检查：同一 bounded 图的实现对齐，以及 bounded 相对 exact 的反例。

## 第三个修改：更低复制成本的事务

`Runner` 现在保存复制快照，容易理解，但全局来源与每个草稿位置都复制一次并不便宜。可以试着为被覆盖的槽位保存 undo 记录，只让真正提交的来源长度前进。

这时需要一起处理局部 K/V、位置标签、Encoder/共享来源、Token 边界和 logits。只恢复其中一个，输出短时间对齐也不能算通过。先让覆写测试失败，再对照完整状态，不要先写速度承诺。

## 真要换模型，先承认状态契约不同

当前 `TinyModel` 不是可以直接塞入任意 Hugging Face 权重的壳。`Runner` 依赖它的因果 Encoder、共享来源与逐层局部状态。换成没有这些状态的模型，应该重述接口与测试，不要把普通 Llama 推理改个名字就叫 DeepInfer 复现。

权重与布局的身份也不能继续沿用旧指纹。不同参数、窗口、布局、恢复模式的状态不可混用。加入真正的 GPU 后端时，设备与 dtype 的有效性也要进入契约，而不是只看 Python 对象还在不在。

## 哪些省略是刻意的

没有训练出的语言能力、概率拒绝采样、并行 GPU batch、CP、多机 KV、持久化会话和 HTTP 服务。这些能力各自有真实的验证门。把另一个项目的功能清单贴进这里，不会让这个核心更完整。

一个扩展应当至少留下三样东西：能走通的用户入口、会因错误实现而失败的检查、准确说明简化的文字。可读规模值得保护，但行数少也不能靠删掉错误路径来实现。

```bash
python examples/engine_batch.py
python -m core_deepinfer generate --input examples/requests.json --trace --json
python -m pytest -q
```

最后再构建、安装到环境，从仓库以外运行一次。源码目录里能 import，不代表 wheel、入口脚本和相对文档已经打包正确。具体记录见[验证说明](../docs/VALIDATION.md)。
